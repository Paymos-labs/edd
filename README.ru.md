# Paymos для Easy Digital Downloads

[English](README.md) | [简体中文](README.zh-CN.md) | **Русский** | [Español](README.es.md) | [Deutsch](README.de.md) | [Türkçe](README.tr.md)

Официальный платёжный плагин Paymos для Easy Digital Downloads. Покупатель выбирает его при оформлении заказа, оплачивает счёт в стейблкоинах на странице Paymos и возвращается в магазин к заказу в статусе ожидания. Заказ переходит в `complete` — только тогда EDD открывает ссылки на скачивание и отправляет квитанцию — после того как подписанный вебхук подтвердит перевод в блокчейне. Сам возврат со страницы оплаты файл не разблокирует.

## Требования

- WordPress 6.5 или новее, протестировано до 7.0 — минимальная версия указана в заголовке `paymos-easy-digital-downloads.php`
- Easy Digital Downloads, объявленный там же как обязательный плагин. Шлюз работает с моделью заказов EDD 3.x
- PHP 7.4 или новее с расширением OpenSSL — учётные данные шифруются по алгоритму AES-256-GCM
- Сайт, доступный из интернета по HTTPS. Вебхук принимает запросы на REST-маршрут вашего домена; уведомления не отправляются на loopback, приватные и link-local адреса
- Аккаунт Paymos, в кабинете которого уже выбран проект этого магазина

## Установка

Скачайте архив `paymos-edd-<version>.zip` со страницы [Releases](https://github.com/Paymos-labs/edd/releases/latest) или из раздела **CMS integration** в кабинете Paymos. Установите его через **Plugins → Add New Plugin → Upload Plugin** (в более ранних версиях WordPress раздел называется **Add New**) и активируйте плагин.

Paymos PHP SDK уже лежит внутри архива, поэтому Composer не нужен. Все мерчанты скачивают один и тот же файл: в нём нет API-ключа, секрета, идентификатора проекта, секрета вебхука, OAuth-токена или кода устройства.

## Подключение

Чтобы подключить магазин, нужна роль с правом EDD `manage_shop_settings` — менеджер магазина или администратор.

1. В кабинете Paymos откройте проект, через который продаёт этот магазин: привязка идёт сразу к нему, отдельного выбора позже не будет.
2. Перейдите в **Downloads → Settings → Payments → Paymos** и нажмите **Connect Paymos**.
3. В открывшейся вкладке подтвердите адрес сайта и проект. Если браузер заблокировал всплывающее окно, ссылка и код подтверждения появятся рядом с кнопкой.
4. Поле **Connection status** заполнится автоматически: активный режим, готовность сред Sandbox и Live, маскированный API-ключ и идентификатор проекта.

Одно подтверждение сразу выдаёт ключи для тестового (Sandbox) и рабочего (Live) режимов. Плагин переиспользует единственный активный платёжный ключ или создаст новый, если его нет, и зарегистрирует вебхук категории Invoice по адресу:

```text
https://your-store.example/wp-json/paymos-edd/v1/webhook
```

Уже существующий вебхук переиспользуется, только если совпадают URL, категория и проект.

Учётные данные хранятся в опции WordPress без автозагрузки и зашифрованы AES-256-GCM на ключах, полученных из солей `auth` и `secure_auth` сайта. Короткоживущий токен авторизации сразу удаляется, а все последующие запросы к Merchant API подписываются через HMAC.

## Настройки

| Параметр | Значение по умолчанию |
|---|---|
| Название на чекауте (Checkout label) | `Pay with stablecoins` |
| Режим (Mode) | Sandbox |
| Webhook URL | Только чтение; регистрируется при подключении |
| Статус подключения (Connection status) | Только чтение |
| Журнал отладки (Debug logging) | Выключен; при включении пишет сообщения Paymos в отладочный журнал EDD |

Поля для ручного ввода секрета и выбора проекта нет — оба параметра приходят после подтверждения подключения.

## Когда открывается скачивание

| Событие Paymos | Заказ в EDD |
|---|---|
| Покупатель выбрал Paymos, заказ записан, корзина очищена | `pending`, заметка с идентификатором счёта |
| `invoice.confirming` | `pending` — `"Paymos payment is confirming."` |
| `invoice.underpaid_waiting` | `pending`, в заметке указаны остаток к доплате и токен |
| `invoice.awaiting_payment` | `pending`, в заметке указано, что подтверждённый перевод откатился в блокчейне |
| `invoice.paid`, `invoice.paid_over` | `complete` — ссылки на скачивание открыты, квитанция отправлена |
| `invoice.underpaid` | `failed` |
| `invoice.expired`, `invoice.cancelled` | `abandoned` — статус EDD для ожидающего заказа, который так и не был оплачен |

При завершении заказа плагин записывает хеш транзакции в блокчейне как ID транзакции EDD и сохраняет метаполя `_paymos_tx_hash` и `_paymos_explorer_url`. Повторное финальное событие по уже завершённому заказу распознаётся как дубль и не добавляет лишних заметок, а пришедшие позже `confirming`, `underpaid`, `expired` или `cancelled` помечаются как проигнорированные и ничего не меняют.

Если сумма или валюта заказа разошлись со счётом, заказ не закрывается. Плагин ставит метаключ `_paymos_amount_mismatch` в значение `yes`, записывает расхождение в заметки заказа и оставляет разбор оператору. До этого момента файлы остаются закрыты.

## Что видит покупатель после оплаты

В квитанции на сайте и в письме о покупке появляется строка **Payment confirmation**: ссылка на обозреватель блоков, если она пришла в уведомлении, либо сам хеш транзакции. Пока хеша нет — а в тестовом режиме Sandbox его не бывает, — строка не выводится.

## Проверка перед запуском

1. Оставьте **Mode** в положении Sandbox и оформите покупку файла на витрине.
2. Найдите этот счёт в кабинете Paymos (тоже в режиме Sandbox) и проведите его кнопками **Pay Full**, **Pay 50%**, **Pay 150%** или **Cancel**. Через магазин пройдут настоящие события жизненного цикла, но средства никуда не перечисляются.
3. Проверьте заказ: статус, заметки и доступность ссылки на скачивание.
4. Переключите **Mode** в Live. Первое подключение уже выдало обе пары ключей, повторная настройка не нужна.

## Вебхуки

Маршрут работает через WordPress REST API и принимает только `POST`. Заголовок `X-Webhook-Signature` проверяется сразу по секретам обеих сред, после чего флаг `is_test` в теле запроса сверяется с той средой, чей секрет прошёл проверку: рабочий вебхук не закроет тестовый заказ, и наоборот. Уже встречавшийся `event_id` подтверждается и пропускается. Финальные события плагин перепроверяет запросом к Merchant API и сравнивает проект, сумму и валюту с заказом, прежде чем что-либо записать.

При ошибке маршрут отдаёт статус, на который отправитель реагирует повтором, ведь именно код не из 2xx удерживает событие в очереди доставки: `401` при неверной подписи или устаревшей метке времени, `400` при ошибке обработки, `500` если секрет вебхука не сохранён. Повторов всего 11 — примерно на 16 часов. Неоплаченные счета опираются на подписанный вебхук `invoice.paid` и не проверяются локальным cron-заданием; если уведомление не дошло за время всех попыток, его можно отправить повторно вручную из кабинета Paymos. А вот незавершённые возвраты плагин локально опрашивает раз в минуту через WP-Cron `paymos_edd_refunds_reconcile` до финального статуса.

## Возвраты

Шлюз поддерживает нативные возвраты в блокчейне через Paymos Merchant API (`/v1/refunds`) в двух режимах:

- `full` — возврат всей оплаченной суммы по счёту;
- `overpayment` — возврат только переплаты по заказу со статусом `invoice.paid_over`, при этом сам заказ остаётся в `complete`.

Средства уходят строго на проверенный адрес кошелька `first_sender`, который Paymos зафиксировал при оплате счёта покупателем. Адрес получателя вручную не вводится, а произвольные частичные возвраты не поддерживаются.

Для завершённого заказа Paymos в **Downloads → Orders** полный возврат `full` запускается через стандартное окно EDD **Initiate a Refund** (выбрав все позиции заказа целиком), а управлять возвратами обоих типов (`full` и `overpayment`) и проверять их статус можно в панели **Paymos refunds** на карточке заказа. EDD создаст локальную запись о возврате и отправит письмо покупателю только после того, как Paymos подтвердит статус `completed` через `/wp-json/paymos-edd/v1/webhook` или минутную задачу WP-Cron `paymos_edd_refunds_reconcile`. В режиме Sandbox можно симулировать финальные исходы возврата (`completed`, `failed`, `cancelled`) без перевода средств.

## Устранение неполадок

**Покупатель оплатил заказ, но файл всё ещё закрыт.** Заказ ждёт вебхук, который не дошёл до сайта. Проверьте, отвечает ли маршрут снаружи: плагины безопасности, HTTP Basic Auth или отключение REST API блокируют запросы без предупреждения, а доставка вебхуков не ходит по редиректам на другой адрес.

**Маршрут отвечает `not_configured`.** В базе нет сохранённых учётных данных и секрета для проверки подписи. Нажмите **Connect Paymos** на странице настроек и завершите подтверждение.

**После правки `wp-config.php` всё перестало работать.** Конверт с ключами зашифрован на солях `auth` и `secure_auth`. Если поменять их или перенести базу на сайт с другими солями, расшифровать данные не получится — подключите магазин заново, чтобы выпустить новый конверт.

**После переезда на новый домен ничего не работает.** Привязанный адрес сайта и зарегистрированный вебхук по-прежнему указывают на старый хост. Повторите подключение уже с нового домена.
